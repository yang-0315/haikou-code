# 软件著作权申请计划

日期：2026-11-23

## 一、最终目标

本项目最终目标调整为申请软件著作权，不再以商业竞争力和联网模型对比结果作为
继续开发的必要条件。

软著申报对象收敛为一个独立软件：

- 软件全称：海南自由贸易港政策法规效力感知检索与问答系统
- 简称：政策效力感知问答系统
- 版本号：V1.0
- 软件类型：应用软件
- 开发完成日期：2026-11-23
- 开发方式：独立开发
- 权利取得方式：原始取得
- 发表状态：按实际情况填写。若 GitHub 仓库在申请前已公开，不应填写“未发表”；
  未发表版本应在提交前停止继续公开传播，并保留首次公开日期证据。

上述登记信息应以申请人的真实身份、实际开发过程和最终申报平台字段为准。

## 二、申报范围

### 建议纳入

- `haikou/` 下的自研 Python 程序；
- `haikou/web/` 下的自研前端页面、脚本和样式；
- `tools/` 下的测试、归档和材料生成工具；
- 必要的架构说明、使用说明和测试说明。

当前自研代码规模：

| 部分 | 文件数 | 行数 |
|---|---:|---:|
| `haikou/*.py` | 74 | 18,430 |
| `haikou/web/*` | 3 | 2,277 |
| `tools/*.py` | 3 | 998 |

现有代码量足以形成规范的源代码材料。

### 必须排除

- `PageIndex/`：MIT 上游子模块，不属于本软件源代码；
- `database/`：政策原文、附件、模型回答和生成索引；
- `.venv/`、`haikou/_vendor/`：第三方运行时和依赖；
- `.env`、API Key、Cookie 和部署凭据；
- 模型生成的原始回答、第三方评审表单和自动生成的索引文件；
- 未经实质整理的自动抓取网页。

## 三、材料清单

### 1. 软件源代码

需要生成：

- `source_inventory.csv`：文件路径、功能说明、行数、SHA-256；
- `copyright_source/`：只包含纳入申报范围的自研源代码；
- `source_listing.pdf`：按每页 50 行排版的源代码；
- `source_listing_first_last_30_pages.pdf`：若完整源码超过 60 页，按申报要求
  提供前 30 页和后 30 页；
- `source_fingerprint.json`：提交快照的提交号、标签、文件哈希和生成时间。

排版要求：

- A4、纵向、单栏、等宽字体；
- 每页 50 行，保留文件名和连续页码；
- 不包含密钥、绝对用户路径和敏感数据；
- 不对第三人源代码作实质改写后冒充原创代码。

### 2. 软件说明书

建议制作 20–30 页 Word/PDF，包含：

1. 软件概述和适用领域；
2. 运行环境与依赖；
3. 安装、配置和启动；
4. 首页与提问入口；
5. 当前效力状态展示；
6. 引用来源和条号展示；
7. 历史时点查询；
8. 拒答与存疑结果；
9. 事项目录查询；
10. 政策更新监控；
11. 数据维护和索引重建；
12. 错误处理；
13. 测试与验收；
14. 已知边界。

说明书截图必须来自当前 V1.0 程序，不能使用第三人产品的界面截图作为软件功能。

### 3. 软件功能截图

最低截图集：

- 软件首页；
- 普通政策问答；
- 带来源条文的回答；
- 已废止文件提示；
- 条文部分失效提示；
- 历史时点回答；
- 语料外问题拒答；
- 事项目录查询；
- 政策更新扫描报告；
- 测试结果汇总。

截图保存在 `copyright_assets/screenshots/`，文件名按功能编号，避免包含个人信息。

### 4. 第三方边界说明

提交前复核并保留：

- `THIRD_PARTY_NOTICES.md`；
- `PageIndex/LICENSE`；
- Python、PDF、模型 SDK、前端依赖的许可证来源；
- `database/` 不纳入源码申明的说明；
- `haikou/_vendor/` 不作为原创代码提交。

### 5. 开发与验收证据

- Git 基线和版本标签；
- 测试批次摘要；
- v4 评测数据与结果；
- 三方案对比报告；
- 说明人工需求定义、架构选择、代码审查和测试验收的文档记录。

AI 辅助代码生成不改变软件申请人的原创权利归属，但应保留人工主导开发过程、
审查记录和最终表达的客观证据。

## 四、版本冻结方案

在生成申报材料前冻结：

- 软件名称：政策效力感知问答系统 V1.0；
- 功能范围；
- 自研源码清单；
- 第三方边界；
- 用户说明书；
- 截图和测试证据。

后续修复不得无版本记录地覆盖申报使用源码。若申报后继续开发，应使用新版本号。

## 五、申请前检查

- [ ] 软件名称和版本号在代码、页面和说明书中一致；
- [ ] 源码清单只包含自研代码；
- [ ] `PageIndex/`、语料和第三方库未混入源码材料；
- [ ] 没有密钥、账号、绝对路径和客户隐私；
- [ ] 代码页数、每页行数和前后页规则符合申报平台要求；
- [ ] 说明书截图与当前源码版本一致；
- [ ] 第三方许可证和版权声明齐全；
- [ ] 版本标签和源码指纹已生成；
- [ ] 申请表中的开发完成日期、开发方式、权利取得方式按实际情况填写；
- [ ] 发表状态与首次发表日期和 Git/GitHub 公开记录一致；
- [ ] 已完成一次从干净环境启动和功能验收；
- [ ] 申报材料 PDF 可打开、页面清晰、编号连续。

## 六、执行顺序

1. **冻结申报范围**：确认软件名称和 V1.0 功能清单；
2. **清理源码**：排除 PageIndex、语料、依赖、密钥和非自研文件；
3. **生成代码清单**：统计文件和行数，生成 SHA-256；
4. **生成源码 PDF**：按 50 行/页排版，生成完整版和前后 30 页版；
5. **完成用户说明书**：图文描述实际操作流程；
6. **补齐截图**：使用当前软件真实运行结果；
7. **准备申请表信息**：软件名称、版本、完成日期、开发方式、权利人；
8. **申报前复核**：第三方边界、隐私、版本一致性和材料完整性；
9. **提交并保存归档**：保留提交版本、申请号和全部材料副本。

## 七、当前可立即执行的下一步

先完成代码申报范围清单和用户说明书目录；两项确认后再生成源码 PDF，
避免名称、版本或功能范围变化导致全部材料返工。

现有测试和对比实验继续保留作为软件验收与开发记录，但不再作为商业竞争力证明。
